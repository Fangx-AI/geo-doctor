# 技能触发率评测

客户端只看 `SKILL.md` 里那行 `description`，就决定要不要加载一个技能。描述写得漂亮但没写用户真正会说的话，技能就**永远不触发**，而且所有结构测试都是绿的：YAML 合法、链接不越界、脚本齐全。这一层只能用「给一批问题、看它选哪个技能」来测。

## 两个集

| 文件 | 条数 | 用途 |
| --- | --- | --- |
| `prompts.json` | 37 | 开发集。调 description 时看这里的漏触发。 |
| `heldout.json` | 21 | 门槛集。**不参与调参**，只在改完之后跑一遍，当作「这次改动是真的更好，还是只是背下了开发集」。 |

每条用例：`id`、`prompt`（用户原话）、`expect`（期望被触发的技能目录名，或 `null` 表示一个都不该触发）。

## 怎么跑

结构检查，不联网、不需要任何 key，CI 每次 PR 都跑：

```bash
node scripts/trigger-eval.mjs
```

量触发率，用本机的 CLI 当裁判（它从 stdin 读一个问题，只在 stdout 输出技能名或 `none`）：

```bash
node scripts/trigger-eval.mjs --judge "claude -p"
node scripts/trigger-eval.mjs --judge "claude -p" --set prompts --limit 5
node scripts/trigger-eval.mjs --judge "claude -p" --report evals/triggers/report.md
```

`--judge` 可以是任何满足上面约定的命令，仓库不配置任何模型 API、也不读取 API Key。

## 结果怎么读

- **漏触发（MISS）**：期望 A，得到 none 或别的技能 → description 少了用户会说的词，或边界没划清。
- **误触发**：`expect: null` 的用例被指到某个技能 → 描述太宽。
- **未解析**：裁判输出不合约定 → 是裁判的问题，不是技能的问题，换命令重跑。

分数不是目的，「哪条用例漏了」才是。每次改完把两个集的分数和漏掉的用例一起写进 PR。

## 基线记录

2026-11-16，裁判 `claude -p`，一题一次：

| 轮次 | 开发集 | 门槛集 | 说明 |
| --- | --- | --- | --- |
| 拆分完成 | 36/37（97%） | 20/21（95%） | 开发集漏 `write-05`（这一行广告有限制、文案哪些话不能说 → none）；门槛集漏 `write-h2`（把散落的参数整理成唯一事实源 → 错判给 `llms-txt`） |
| 修完 description | 37/37 | 21/21 | 见下的改动 |

两处改动都指向同一类问题：**内容边界没在描述里说清**。

1. `ai-content-writer` 补上「官网、销售话术说法不一致时整理成唯一事实源」和「金融/医疗/教育/广告等受管行业哪些话不能说」，把合规与事实卡的触发面写进去。
2. `llms-txt` 明确写「从已经存在的（或由 ai-content-writer 确认过的）事实卡出发」，`ai-content-writer` 对应地写「把卡变成站点文件去找 llms-txt」。

`evals/triggers/report.md` 是最近一次运行的原始输出，提交它等于提交证据，不是提交分数。

## 纪律

- 改 description 只看开发集的漏触发，**不要对着门槛集调**。
- 门槛集用一次就消耗一次。上面第二轮用掉了「事实卡 vs 事实源文件」这条边界，下次动这两个技能要**先补新的门槛用例**再改。
- 一个裁判只代表一个模型。换客户端（Codex、Kimi Code、Cursor）要各自记录，不能拿这里的 100% 说「所有客户端都能触发」。

## 局限

- 每个用例只问一次，没有重复采样，模型抖动没有量化。
- 裁判只看到 description，没有会话历史；真实客户端会带上下文，触发率通常更高，所以这里的数字是**下限**。
- 37 + 21 条覆盖不了长尾，用户换一种说法就可能漏。发现漏触发就把那句话加成新用例，再改描述。
