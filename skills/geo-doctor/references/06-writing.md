# 第 6 步 · 开方·写内容：只写缺口，只用事实

**目的：** 针对诊断出的缺口，写出 AI 愿意整段引用、用户读了能做决定的内容。可以一次写一批，但**一篇对应一道不同的缺口题**，不是同一篇换个说法发很多遍。

## 写之前

- 只写 `geo/diagnosis.md` 里竞品缺口清单和处方列出的题目。用户说"都写了"时，按缺口清单批量写，**一批最多 20 篇**，按处方优先级排；用户没说时，先写处方前 3 道，写完问要不要继续。
- 只用 `geo/fact-card.yaml` 里状态为"已确认"的事实。需要的事实是"未知"，先问用户，不要补全。
- 先看第 5 步竞品缺口清单里"推荐竞品时被引用的那一段"：是清单、对比表、问答还是测评，照这个形式写，并且要比它更具体、更新。

## 按平台选形式

| 形式 | 适合的缺口 | 发布位置（详见第 7 步） |
| --- | --- | --- |
| 官网问答段落 / FAQ | B 类事实题、C 类"适不适合" | 官网、帮助中心 |
| 对比页 | "A 和 B 哪个好""XX 的替代品" | 官网、知乎文章 |
| 问答型文章 | A 类推荐题 | 公众号、知乎、头条号、百家号 |
| 知乎回答 | 知乎上已有的同类问题 | 知乎（用实名或机构号，写明身份） |
| 技术文章 | 开发者工具的使用、对比、排错 | CSDN、掘金、官方博客 |
| 应用商店描述 | 名称、价格、能力说法不一致 | 各应用商店 |
| 视频口播稿 | 豆包场景（抖音）、B 站用户 | 抖音、B 站、视频号 |

## 写法规则

### 三个必做项：让 AI 更愿意引用你

GEO 论文测试了多种改写方法，效果最好的三种是**加统计数据、注明来源、加引语**，在实验中让内容在 AI 回答里的可见度最高提升约 40%；堆关键词反而更差（📊 [Aggarwal 等，KDD 2024](https://arxiv.org/abs/2311.09735)）。注意这是实验室条件下、内容已被检索到之后的结果，不是效果承诺；后续研究发现不同 AI 之间差异很大。

有相关的已确认材料时，每篇草稿都要用上这三条；数据和引语只能来自事实卡或可核实的公开来源。材料不够时宁可少写，不为了凑数编造或塞进无关数据，并在草稿末尾的核对表里写明缺什么，请用户补充：

- **具体数据**（有就尽量写 2 个以上）：价格、人数、版本、日期、用户自己的真实统计（例如“2026 年 9 月共有 1,200 家门店在用”），不编、不估。
- **注明来源**：行业数据、标准、第三方评价都附链接。
- **引用一句权威或真实用户的话**：官方文档、媒体报道、经授权的客户原话，注明出处；没有就不写，不能编。

### 其他写法

1. **第一句就给答案。** 小标题用用户的原话提问，下面第一句直接回答。
2. **一段只讲一件事。** AI 是按段落挑内容的，每段都要能单独被摘走、单独成立。
3. **写具体的名词和数字。** 产品名、版本号、价格算式、人数、日期，不写"多种""丰富""大量"。
4. **能力后面紧跟限制。** "支持离线编辑（仅桌面端）"。
5. **写清不适合谁。**
6. **给出处。** 引用的数据、标准、第三方评价都附链接。
7. **写日期。** 价格、版本类内容写"截至 X 年 X 月"。
8. **不用无法证明的词：** 最好、第一、领先、唯一、100%、全网、颠覆。

### 改写示例

- 改前：XX 笔记是一款功能强大、体验极致的知识管理工具，深受广大用户喜爱。
- 改后：**20 人以内的团队适合用 XX 笔记吗？** 适合。XX 团队版 299 元/月含 20 人，超出每人每月 20 元，支持 Windows、macOS 和网页端，可导出 Markdown。不适合需要私有化部署的企业：XX 目前只提供云端版本（截至 2026 年 10 月）。

后一段一次回答了"适不适合、多少钱、支持什么平台、能不能导出、谁不适合"五个子问题，每个都能被 AI 单独引用。

## 草稿格式（批量发布要用）

每篇存为 `geo/drafts/<slug>.md`，开头用 `---` 包一段文章信息，正文用 Markdown：

```markdown
---
title: 不用联网也能记账吗？小鹿记账离线模式说明
slug: offline-budget-app
question: 有没有不用联网也能用的记账 App？
description: 一句话说清这篇回答了什么（搜索结果和 AI 摘要会用到）
lang: zh
platforms: [site, zhihu, toutiao]
facts: [B01, F03, X02]
tags: [记账, 离线]
brand: 小鹿记账
status: draft
---

正文第一句直接回答问题……

## 核对表

| 句子 | 事实卡编号 |
| --- | --- |
```

- `slug` 只用小写字母、数字和连字符，会成为官网页面地址的一部分。
- `platforms` 写这篇要发到哪里：`site`（自己的官网）、`zhihu`、`wechat`、`toutiao`、`baijiahao`、`sohu`、`xiaohongshu`、`juejin`、`medium`、`reddit`。按第 7 步目标 AI 的信源选，不要每篇都写满。
- `facts` 写这篇用到的事实卡编号。
- `status` 先写 `draft`。**用户读过、确认事实无误后，才改成 `confirmed`**，只有 confirmed 的草稿会被发布或打包。不要替用户改。
- 正文里 `## 核对表`（或"核对清单""发布前核对"）这个标题及以下的内容只给用户核对，脚本发布时会自动去掉。HTML 注释 `<!-- -->` 也不会发布。

## 写完自检（逐条过，写进草稿末尾）

1. **核对表**：每一句事实 → 对应事实卡编号。对不上的删掉或改掉。
2. **合规**：对照 [compliance.md](compliance.md) 的自检清单。
3. **标注**：提醒用户按平台要求标注 AI 生成，发布前自己通读一遍。

## 用 API 批量起草（可选）

用户有模型 API Key、缺口题很多时，可以先让脚本按缺口起草，再由你逐篇核对、修改：

```bash
DEEPSEEK_API_KEY=… node <技能目录>/scripts/geo-autopilot.mjs gaps            # 列出缺口题（读 geo/runs.csv 里最近一批 API 采样）
DEEPSEEK_API_KEY=… node <技能目录>/scripts/geo-autopilot.mjs write --ai deepseek --max 3
```

- 只给还没有草稿的缺口题写，每题一篇；提示词只放事实卡里"已确认"的事实，并要求不编数字、不写评价、写清不适合谁。
- 写好的稿存进 `geo/drafts/`，带 `qid`（题号）和 `generated_by`（用了哪个模型），状态是 `draft`，并自动跑一遍下面的检查。
- 这只是初稿：你仍要按本页规则逐句核对事实编号，删掉事实卡里没有的说法，再请用户确认。

## 用脚本检查整批草稿

能运行命令时，写完一批先跑（`scripts/geo-publish.mjs` 在本技能目录里，也可以用 npx）：

```bash
node <技能目录>/scripts/geo-publish.mjs check geo/drafts
# 或：npx -p github:Fangx-AI/geo-doctor geo-publish check geo/drafts
```

它会读 `geo/fact-card.yaml`，检查每篇：

- ❌ **错误**（必须改）：缺标题、slug、问题或状态；slug 格式不对或重复；平台名写错；还有"[待确认]""TODO"之类占位符；用到了事实卡里没有或状态不是"已确认"的编号
- ⚠️ **提醒**（逐条判断）：最好、第一、保证、100% 等需要证据的词；像是引用用户评价的句子；正文太短；没写 description 或 facts；**两篇正文相似度超过 60%**（同一内容换说法重复发是低质内容，合并或重写）

把错误全部改掉，提醒逐条判断，再请用户确认。不能运行命令时，按同样的清单人工逐篇检查。

## 完成标准

- 每篇草稿存为 `geo/drafts/<slug>.md`，开头有文章信息，末尾附核对表，`check` 没有错误
- 告诉用户：写了几篇、分别解决哪道题、有哪些提醒需要他判断；请他读完后把确认的稿件改成 `status: confirmed`，然后进入第 7 步发布
